# Hundred-User General Doctrine

Status: research-only doctrine. No live execution, publication, spend, provider call, credential use, adoption, merge, or Runtime authority is granted.

## Purpose

The first conquest stage is not scale. It is proving that one narrow wedge creates a repeatable loop for the first 100 real users.

Working metaphor:
- `HUNDRED_USER_GENERAL` = first 100-user wedge;
- promotion is earned by measured repeat behavior, not by attention alone;
- one viral spike does not count as promotion.

## Default first wedge under current research

Current hypothesis leader:

`FASHION_TREND_COMMENTARY_TO_OWNED_WARDROBE_ACTION`

Loop:
1. character-led trend commentary or verification;
2. external discovery;
3. user asks: "Can I actually wear this / recreate this?";
4. owned service maps the trend to the user's own wardrobe/preferences;
5. user saves one actionable outfit/state;
6. service remembers state and reduces the next decision cost;
7. user may create a shareable output;
8. external rediscovery feeds the next cycle.

This is a research hypothesis, not an adopted business.

## What the first 100 must prove

The first 100 users are valuable only if they reveal repeatable behavior.

Promotion evidence should include:
- `first_value_rate`: user reaches one useful owned result;
- `saved_state_rate`: user saves wardrobe/style state;
- `7d_return_rate`: user comes back within 7 days;
- `second_action_rate`: user uses the service for a second distinct decision;
- `share_output_rate`: user creates or shares a reusable output;
- `organic_return_path_rate`: user returns without requiring paid reacquisition;
- `premium_interest_signal_rate`: user voluntarily reaches a paid-value boundary;
- `owner_minutes_per_active_user`: operational burden;
- `policy_or_safety_incidents`: must remain bounded and reviewed;
- `general_ai_substitution_rate`: percentage of jobs users can satisfy just as well with a generic AI prompt.

## No vanity promotion

The following do not promote the stage on their own:
- views;
- likes;
- follower count;
- one influencer repost;
- one viral video;
- app installs without first value;
- email capture without return behavior;
- model-predicted revenue without settled outcomes.

## Promotion logic

`HUNDRED_USER_GENERAL -> NEXT_STAGE_CANDIDATE` requires measured evidence that:
- repeat use exists;
- owned state gets more valuable over time;
- acquisition is not purely paid/platform-rented;
- generic AI does not fully replace the owned loop;
- user value exists before monetization friction;
- legal/policy/safety posture remains acceptable;
- owner burden does not explode with user count.

Exact thresholds are experiment-specific and must be frozen before live testing. No thresholds in this doctrine authorize a live test.

## Current strategic twist

Fresh 2026 fashion research strengthens three observations:
- fashion discovery increasingly happens through short-form/social surfaces;
- AI shopping/style assistance is becoming commodity capability;
- resale, wardrobe value, individuality, authenticity, and human taste remain important differentiators.

Therefore the wedge should not be "AI recommends clothes".

The stronger wedge is:

`character taste + trend verification + user's existing wardrobe/state + next actionable decision + shareable result`

## Fail / pivot triggers

Before any live test, define bounded triggers such as:
- high first-value but weak 7-day return -> utility is transactional, not compounding;
- high views but weak owned visits -> character/content may entertain without transferring intent;
- high owned visits but weak saved-state -> owned moat too weak;
- high generic-AI substitution -> simplify or pivot to stateful/transactional utility;
- heavy manual styling effort -> automation or narrower wedge required;
- policy fragility or deceptive targeting dependence -> redesign, not workaround;
- monetization requires artificial obstruction -> reject that monetization path.

## Authority boundary

Research can continue autonomously on repository-only design, simulation, evidence packets, metrics, test schemas, and retrospective logic.

Owner action becomes necessary only when the next useful step requires a real live effect: publication, external account creation/contact, credentialed platform/API use, spending, live user recruitment, live data collection, payment collection, canonical adoption/merge, or Runtime activation.
